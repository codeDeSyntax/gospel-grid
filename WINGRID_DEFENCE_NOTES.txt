Core Guiding Philosophy of Wingrid
----------------------------------
"To make live presentations more professional and significantly smarter by lifting off 
longstanding display bottlenecks and introducing real-time AI context intelligence."

Wingrid is NOT simply a screen sharing application (like Zoom or Teams).
Wingrid is NOT a cumbersome broadcast studio mixer (like OBS Studio or vMix).
Wingrid is NOT a generic remote desktop tool.

Wingrid is an Intelligent Multi-Window Presentation Orchestrator and Live Production Studio.
It gives a single operator the power to select, compose, arrange, hide/show, augment, 
and project live Windows applications seamlessly to secondary displays without exposing 
their personal desktop or wrestling with Windows display settings.


Simple Project Description (Elevator Pitch)
-------------------------------------------
Wingrid (v2.2.46) is a high-performance Electron desktop application engineered to transform 
live presentations in churches, classrooms, conference halls, and hybrid streams.

It enables a single operator to natively detect running Windows applications, selectively 
compose multiple live sources into clean audience grid layouts (Single, Dual, Triple, Quad), 
and project them to secondary displays via GPU hardware acceleration.

It eliminates manual production friction through built-in live presentation tiles (countdown 
timers, image galleries, broadcast overlays, real-time speech-to-text captions), integrates 
a real-time AI Context Intelligence producer powered by AssemblyAI & Groq (Llama 3.1) that 
extracts scriptures, lower-thirds, and key quotes in ~200ms, and enables local LAN discovery 
with permission-gated WebRTC peer-to-peer remote screen collaboration.


The 4 Core Bottlenecks Wingrid Lifts Off
----------------------------------------
In live presentation environments (churches, classrooms, boardrooms, live streams), operators 
frequently need to present content from multiple applications at once (e.g., slides, Bible software, 
browser feeds, countdown timers, speaker notes).

Existing tools force operators into four critical bottlenecks:

1. Single-Source Sharing Restrictions:
   - Problem: Standard meeting and projection tools restrict presentation to one application or 
     force sharing the whole screen. Presenting two or more applications at once is impossible without 
     messy window resizing.
   - Wingrid's Solution: Selective Multi-Window Layout Engine (1, 2, 3, or 4 windows) with instant 
     per-window Hide/Show toggles.

2. Display Mode Conflicts & Screen Flickering:
   - Problem: Different applications expect different Windows display modes (some need Extended mode, 
     others need Duplicate mode). Operators repeatedly press Win+P during live events, causing screen 
     flickering, resolution drops, and embarrassing delays.
   - Wingrid's Solution: "Two Windows, One Operator" Dual-Window Architecture. The operator works 
     privately on the Control Dashboard (Screen 1), while the audience sees a clean, frameless GPU 
     output (PublishedLayout on Screen 2). The operator never touches Windows display modes live.

3. Privacy & Desktop Exposure:
   - Problem: Sharing the entire desktop exposes notifications (WhatsApp, emails), desktop icons, 
     taskbars, private files, and uncurated background windows to the audience.
   - Wingrid's Solution: Strict Window Isolation. Wingrid captures only the selected application 
     windows directly at the compositor level. The audience never sees the operator's desktop or private apps.

4. Manual Content Augmentation Overhead:
   - Problem: Displaying supporting context (scriptures, speaker lower-thirds, statistics, timers, 
     key quotes) during a talk traditionally requires extra production crew members manually typing 
     or switching complex OBS scenes in real time.
   - Wingrid's Solution: Automated AI Context Intelligence. Streams live speech, detects key points in 
     ~200ms via ultra-fast Groq LLM inference, and gives the operator 1-click "Push to Live" broadcast cards.


Wingrid's Solution & Architecture Pillars
-----------------------------------------
1. Native Windows Window Enumerator:

     with aspect-ratio preservation and live per-window visibility toggles.

   - Control Studio on the primary monitor vs. Pristine Frameless Output (`PublishedLayout`) on the projector/secondary monitor.

4. GPU-Accelerated Video Pipeline (30-60 FPS):
   - Direct `desktopCapturer` video streams rendered through native Web Audio/Video APIs (`getUserMedia`)

5. AI Context Intelligence & Automated Producer (v2.2.46):
   - Real-time speech ingestion via 16kHz PCM audio worklet.
   - Streaming STT with AssemblyAI WebSocket integration.
   - Instant extraction (~200ms) of scriptures, speaker lower-thirds, statistics, and quotes via Groq LPU (Llama 3.1).
   - 8+ dynamic responsive broadcast card layouts with 1-click Push/Hide controls.

6. Built-In Presentation Feature Tiles:
   - Countdown Timers, Stopwatches, and Clock grid tiles.
   - Local Image Gallery projection tile with fit/fill modes.
   - Real-time Speech-to-Text Captions rendered as a layout tile or floating draggable orb.

7. Network-Aware LAN Discovery & WebRTC Collaboration:
   - Discovers nearby Wingrid instances over local network (mDNS / LAN WebSocket signaling).

8. Enterprise-Grade Security & Key Protection:
   - Encrypts API keys at rest using operating system native cryptography (Electron `safeStorage` via Windows DPAPI).


How Wingrid Beats Existing Solutions (Competitive Analysis)
-------------------------------------------------------------
When examiners ask: "Why not use OBS, Zoom, ProPresenter, or Windows Snap?", use these exact distinctions:

1. Wingrid vs. Video Conferencing Tools (Zoom, Microsoft Teams, Google Meet):
   - Single-Source Bottleneck: Zoom/Teams forces sharing 1 window or the entire desktop. Wingrid composes 1 to 4 live windows in responsive grid layouts.
   - Privacy & Notification Exposure: Sharing full screen in Zoom exposes WhatsApp, email popups, taskbars, and personal files. Wingrid isolates window textures directly; the desktop is NEVER visible.
   - No Secondary Display Routing: Zoom has no concept of projecting a clean, frameless output to a physical secondary monitor while keeping the control studio private. Wingrid uses a native "Two Windows, One Operator" display architecture.
   - Cloud Dependency & Latency: Zoom routes video through cloud servers with compression and internet dependency. Wingrid runs 100% locally on the GPU (30-60 FPS) and uses local P2P WebRTC over LAN.

2. Wingrid vs. Broadcast Production Suites (OBS Studio, vMix, Wirecast):
   - Steep Learning Curve: OBS requires manual scene creation, source cropping, audio mixer configuration, and complex canvas transformations. Wingrid is zero-configuration: instant window detection and 1-click grid assignments.
   - High CPU/GPU Overhead: OBS encodes and renders full broadcast canvases, causing laptop fans to spin and systems to lag during lectures/church services. Wingrid uses lightweight GPU request-coalesced window capture tailored for physical displays.
   - Manual Content Creation: OBS requires a second human operator to manually type lower-thirds, scriptures, and timers. Wingrid features an automated AI Context Producer that listens to speech and auto-generates broadcast cards in ~200ms.

3. Wingrid vs. Church & Worship Presentation Software (ProPresenter, EasyWorship):
   - High Cost: ProPresenter licenses cost $400-$1,000+ with recurring seat fees. Wingrid is open, modern, and accessible.
   - Slide-Centric vs. Live-Window Centric: Worship tools are built for static lyrics and slides. Presenting external live applications (browsers, live coding, Zoom remote guest, Bible app) is clunky and awkward. Wingrid treats every running Windows application as a first-class live video source.
   - No Live Speech AI Intelligence: Traditional worship tools cannot listen to a speaker's voice to auto-generate context cards, scriptures, and lower-thirds in real time.

4. Wingrid vs. OS Window Managers (PowerToys FancyZones, Windows Snap Layouts):
   - Single-Canvas Limitation: Snap layouts arrange windows on the same physical desktop, keeping window title bars, taskbars, and background clutter visible to the audience. Wingrid renders a borderless, pristine output on the projector.
   - Eliminates Display Mode Toggling: Forcing apps onto a projector via Windows Snap requires toggling Win+P (Duplicate/Extend), causing screen flashing and resolution resets. Wingrid renders directly to secondary display coordinates without changing Windows display modes.

Technical Deep-Dive: Key Architectural Subsystems
-------------------------------------------------
1. Two Windows, One Operator Model:
   - The Controller Window runs the management dashboard with Redux Toolkit store.
   - The Published Window(s) run as lightweight, borderless fullscreen renderer instances.
   - State synchronization flows across Electron IPC (`update-projection-state`), ensuring zero lag between operator clicks and audience view updates.

2. WGC Capture & Performance Optimization:
   - In v2.2.46, an in-flight request coalescing registry shares promises across simultaneous capture requests, thumbnail resolutions are capped to 640x360, and synchronous stdout I/O is eliminated.
   - Video streaming relies on native GPU `getUserMedia` MediaStreams, maintaining 60 FPS without CPU strain.

3. AI Context Intelligence Pipeline:
   - Audio Capture: 16kHz 16-bit linear PCM downsampled in renderer via `AudioContext`.
   - Streaming STT: Main process streams PCM chunks over WebSocket to AssemblyAI, receiving punctuated turns.
   - Fast Extraction: Buffered transcript turns are debounced by 3.5s and dispatched to Groq API (Llama 3.1) with strict JSON schema enforcement.
   - Projection: Formatted JSON card is dispatched to Redux and transmitted via IPC to `PublishedLayout.tsx`.

4. Secure Key Management (DPAPI):
   - Keys are encrypted on disk via Electron's `safeStorage.encryptString()`, using Windows DPAPI.
   - Raw keys are kept in the Node.js main process and never exposed to the renderer DOM.

5. WebRTC Peer-to-Peer Streaming:
   - Embedded WebSocket signaling server negotiates SDP offer/answers and ICE candidates over local LAN.
   - Once connected, MediaStreams travel directly peer-to-peer via WebRTC DTLS/SRTP encryption.


Frequently Asked Defence Questions & Expert Answers
---------------------------------------------------
Q: What is the core problem Wingrid solves?
A: Wingrid eliminates fragmented and unprofessional presentation workflows. In multi-application environments like churches and lecture halls, operators struggle with switching Windows display modes, exposing unwanted desktop content, and being restricted to sharing single windows. Wingrid enables curated multi-window composition, native display routing, AI context augmentation, and LAN collaboration.

Q: How is Wingrid different from OBS Studio?
A: OBS is designed for video recording and livestream broadcast mixing with complex scene graphs and high CPU overhead. Wingrid is designed for presentation orchestration and display routing for non-technical operators: instant window detection, single-click grid layouts, native monitor assignment, presentation tiles, and automated AI context cards without complex scene engineering.

Q: How is Wingrid different from Zoom or Microsoft Teams?
A: Zoom and Teams are meeting communication platforms that typically share one window or the entire desktop. Wingrid is a presentation compositor that allows multiple live application windows to be selected, curated into custom grid layouts, and projected locally or shared over LAN before broadcasting.

Q: How does Wingrid achieve high projection performance without freezing the system?
A: Wingrid leverages a GPU-accelerated video pipeline. Application window feeds are captured via native MediaStreams (`getUserMedia` with source IDs). Video decoding and composition are offloaded to the GPU. Additionally, in v2.2.46, request coalescing on `desktopCapturer` prevents Windows Graphics Capture session storms and DWM composition stalls.

Q: How does multi-display routing work technically?
A: Electron's `screen.getAllDisplays()` queries native Windows monitor coordinates. The main process spawns a frameless fullscreen `BrowserWindow` on the target display coordinates `(x, y)` with `?layoutId=...`. IPC broadcasts layout and state changes from the dashboard in real time.

Q: How does the AI Context Intelligence engine work?
A: The renderer captures microphone audio, resamples it to 16kHz PCM, and streams it to AssemblyAI via WebSocket in the Electron main process. The resulting punctuated transcript is debounced and sent to Groq (Llama 3.1) using structured JSON schema prompts. In ~200ms, Groq extracts scriptures, quotes, lower-thirds, or statistics, which the operator can project with a single click.

Q: How are API keys secured in the application?
A: API keys are encrypted at rest using Electron's `safeStorage` API, which leverages Windows DPAPI (`CryptProtectData`) tied to the user's OS credentials. The keys reside exclusively in the main process and are never sent over IPC to the renderer DOM.

Q: Why was WebRTC used for remote screen sharing?
A: WebRTC enables direct peer-to-peer media streaming across the local area network. After WebSocket signaling exchanges SDP descriptors, video streams flow directly between machines with ultra-low latency, keeping high-bandwidth video off third-party cloud servers.

Q: What makes this project challenging and worthy of a Level 400 Final Year Project?
A: It integrates diverse computer science disciplines into one cohesive desktop system: native OS window capture APIs, multi-monitor coordinate math, GPU-accelerated media streaming, real-time WebRTC networking, mDNS service discovery, streaming speech recognition, LLM context extraction, DPAPI cryptography, Redux state architectures, and production application packaging.
