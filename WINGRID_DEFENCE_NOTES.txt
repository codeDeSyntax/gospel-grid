Core Identity of the Project
----------------------------
Wingrid is not simply a screen sharing application.
Wingrid is not simply a remote desktop application.
Wingrid is not simply a projection tool.

Wingrid is a multi-window presentation orchestration system designed for
environments where one operator needs to select, arrange, project, and manage
content from multiple live Windows applications without exposing the full
desktop or repeatedly changing Windows display settings.

The main value of Wingrid is controlled presentation composition.


Simple Project Description
--------------------------
Wingrid (v2.2.41) is an Electron-based desktop application that allows an operator
to detect running Windows application windows, select specific live sources,
arrange them into clean audience layouts, and project the curated output to
secondary displays. It also supports network-aware features such as detecting
nearby Wingrid devices on the local network and requesting permission-based
remote screen viewing through WebRTC, alongside live speech-to-text captions,
timers, overlay text, and media projection.


Main Problem Statement
----------------------
In live presentation environments such as churches, classrooms, teaching spaces,
stream setups, and hybrid meetings, operators often need to present content from
different applications at the same time.

However, existing tools usually create three major problems:

1. Different applications expect different display modes.
   Some applications work better in extended display mode, while others are
   easier to manage in duplicate mode. This forces the operator to keep changing
   Windows display settings during live use.

2. Online meeting platforms usually allow only one screen or one application
   window to be shared at a time.
   This makes it difficult for a host to present multiple live sources as one
   curated layout.

3. Sharing the entire desktop can expose private or unwanted content.
   Notifications, files, taskbars, desktop icons, or unrelated applications may
   become visible to the audience.

Wingrid solves these problems by allowing the operator to choose specific live
application windows, compose them into a controlled layout, and project only the
curated output.


Original Problems Identified
----------------------------
Problem 1:
In presentation environments where different applications are used, different
applications may require different display modes. For example, in a church
setting, one application may require extended display mode while another may be
easier to use in duplicate display mode. The operator is forced to keep switching
between display modes, which wastes time and creates room for mistakes.

Problem 2:
On online meeting platforms, a host is usually limited to sharing one screen or
one application window at a time. If the host wants to show multiple windows
together, they often have to share the entire screen or manually switch between
windows. This is inefficient and can expose unwanted desktop content.


Wingrid's Solution
------------------
Wingrid provides a controlled presentation workspace where an operator can:

1. Detect available application windows on Windows operating system natively.
2. Select only the windows needed for presentation.
3. Arrange selected windows into curated layouts (Single, Dual, Triple, Quad grid).
4. Project the final layout to an audience display or dedicated external monitor.
5. Keep the controller view separate from the audience view (Two Windows, One Operator architecture).
6. Avoid switching between Windows duplicate and extend display modes.
7. Add supporting presentation features such as timers, images, captions, and text overlays.
8. Stream live speech-to-text captions via AssemblyAI, local Whisper server, or Web Speech API.
9. Detect nearby Wingrid devices on the same local network automatically.
10. Request permission-based remote screen viewing from another Wingrid machine via WebRTC.


Strong Defence Summary
----------------------
Wingrid solves the problem of fragmented presentation workflows. Instead of
forcing operators to switch Windows display modes, expose their desktop, or
share only one application at a time, Wingrid allows multiple live windows to be
selected, arranged, projected, and remotely viewed in a controlled way. The
system is designed for churches, classrooms, teaching spaces, streams, and hybrid

What Makes Wingrid Different
----------------------------
Wingrid should not be presented as a normal screen sharing tool.

The difference is that Wingrid focuses on curated multi-source presentation.

Normal screen sharing:
- Usually shares one screen or one application window.
- Often exposes the desktop if full screen sharing is used.
- Does not provide proper local projection control.
- Does not solve display-mode switching for different applications.

Wingrid:
- Allows multiple live application windows to be selected.
- Combines selected windows into one curated projection layout.
- Keeps the operator/controller view separate from the audience view.
- Routes projection output cleanly to target display monitors natively.
- Provides high-performance GPU MediaStream rendering (30-60 FPS live projection).
- Adds presentation-specific features like timers, images, live captions, and text overlays.
- Adds LAN device detection and permission-based WebRTC remote viewing.

Comparison With Existing Tools
------------------------------
OBS Studio:
OBS can combine multiple sources, but it is designed mainly for broadcasting and
recording. It is powerful, but it may be too complex for simple live projection
workflows. Wingrid focuses on fast operator control, direct application-window
selection, projection display routing, and presentation-specific use cases.

Zoom / Microsoft Teams / Google Meet:
These platforms are designed for meetings. They usually allow one window or one
screen to be shared at a time. Wingrid focuses on preparing a composed
multi-window layout before projection or sharing.

Windows Display Settings:
Windows allows duplicate and extended display modes, but it does not provide an
application-level presentation composition workflow. Wingrid reduces the need to
manually switch display modes for different applications.

Remote Desktop Tools (AnyDesk / TeamViewer):
Remote desktop tools are designed for controlling or viewing another computer's desktop.
Wingrid's remote feature is not a full remote access tool; it supports presentation
workflows by allowing Wingrid devices on the same network to discover each other and
request approved screen/window viewing via WebRTC without granting remote keyboard/mouse control.


Why the Project Is Suitable for a Final Year Project
----------------------------------------------------
Wingrid is suitable as a final year project because it combines several
technical areas into one practical desktop software system:

1. Desktop application architecture using Electron 33, React 18, Vite, and TypeScript.
2. Native desktop integration for window enumeration, icons, and display metrics.
3. High-performance live media capture & GPU stream rendering (`desktopCapturer` & `getUserMedia`).
4. Multi-window layout composition algorithms (Single, Side-by-side Dual, Triple, Quad 2x2 grid).
5. Native multi-display routing across target physical monitors.
6. Inter-process communication (IPC) with security isolation (`contextBridge`).
7. Complex state management using Redux Toolkit (app, grid, window, captions, notification, projection, ui slices).
8. Real-time speech-to-text transcription via WebSocket streaming (AssemblyAI Node integration, local Whisper server, Web Speech API).
9. Local network discovery of Wingrid devices via mDNS / LAN signaling.
10. WebSocket signaling & WebRTC peer-to-peer media streaming.
11. Permission-based remote screen viewing for user privacy and security.
12. Application distribution engineering: `electron-builder` NSIS packaging, auto-updating via GitHub Releases (`electron-updater`), and system tray lifecycle integration.

This demonstrates that Wingrid is a complete desktop system touching operating system
APIs, media streaming pipelines, real-time networking, AI speech services, security decisions,
and real-time user workflows.

How to Explain UI & Technical Architecture
------------------------------------------
1. Main Dashboard UI & Layout Structure:
   - Screen State Machine in `App.tsx`: welcome -> dashboard -> published layout.
   - Top Header (`TitleBar`): Displays active window count, search refresh countdown, live projection controls (Publish Layout, Close Projection, Blackout F6, Freeze F7, Undo/Redo), app settings toggle, and auto-update status indicator.
   - Left Sidebar (`WindowPicker`): Resizable 300px–600px sidebar rendering all enumerated Windows application windows with live app icons, titles, thumbnails, pin/focus controls, and search filtering.
   - Right Main Area (`InspectorPanel`): Contains the Feature Rail and active workspace panel.
     - Feature Rail: Vertical icon bar providing one-click access to:
       1. Main Layout (`autofit`): Multi-display composition canvas (`AutoFitWindowLayoutOptimized`) showing real detected physical monitors and layout grid assignments.
       2. Text Overlay (`overlay`): Audience message banner composer with style and opacity options.
       3. Timer Feature (`timer`): Countdown timers, stopwatches, and current clock virtual grid tiles.
       4. Live Captions (`captions`): Speech-to-text microphone controls and caption customization.
       5. Remote Screens (`remote`): LAN peer device discovery list, manual IP connection, and WebRTC streaming panel.
       6. Image Projection (`image`): Local image directory selector for background/tile projection.
   - Global Floating Controls: `FloatingCaptionsOrb` (floating draggable mic/caption orb) and `NotifierContainer` (toast notifications).

2. Two Windows, One Operator Architecture:
   - Control Window: Maximized dashboard on laptop/operator screen.
   - Published Window(s): Frameless fullscreen `BrowserWindow` instances routed to target external monitors via `?layoutId=...`.
   - Real-time IPC state sync ensures any dashboard change immediately reflects on the published projection window.

3. High-Performance Media Pipeline:
   - Initial versions polled base64 thumbnails across IPC, causing high CPU usage.
   - Current architecture (v2.2.41) passes native window capture source IDs via `desktopCapturer` to renderer `navigator.mediaDevices.getUserMedia` MediaStreams.
   - Video decoding, composition, and rendering are offloaded to GPU hardware acceleration.

4. Remote Screen Viewing Pipeline:
   - LAN Device Discovery: mDNS / UDP broadcast or embedded WebSocket server detects nearby instances automatically.
   - WebSocket Signaling: Signaling server handles initial SDP offer/answer exchange and ICE candidates.
   - WebRTC Peer Connection: Direct P2P media streaming between machines after approval, keeping video traffic off central servers.

5. Speech-to-Text Architecture:
   - AssemblyAI integration runs in the Electron main process via Node WebSocket to protect API keys from renderer exposure and bypass browser CORS restrictions.
   - Microphone audio chunks are streamed to the backend transcriber service, which dispatches real-time text back to Redux `captionsSlice` over IPC.


Security and Privacy Points
---------------------------
Wingrid is designed around controlled visibility and privacy-conscious presentation:

1. Selective Window Exposure: Does not automatically project or share full desktop; operator selects exact application windows.
2. Controller/Audience Separation: Operator interface (dashboard, notifications, file browser) is never visible on the projection output.
3. Permission-Gated Remote Viewing: Remote peers cannot view screens without explicit recipient confirmation.
4. Selective Remote Sharing: The recipient chooses specifically which window or screen to stream to the requester.
5. View-Only Remote Streaming: No remote keyboard, mouse, or system input control is granted to remote peers.

Important Defence Line:
"Wingrid is designed around controlled visibility. The audience or remote viewer
should only see what the operator or sharing user intentionally exposes."

Question:

Wingrid solves the problem of fragmented presentation workflows where operators

Answer:
OBS is a powerful broadcast production tool, but Wingrid targets a simpler and

classrooms, teaching spaces, and hybrid presentations. Wingrid focuses on
operator efficiency, native display routing, and controlled projection rather than full
broadcast production complexity.


Question:
Why not just use Zoom or Teams screen sharing?

Answer:
Zoom and Teams are meeting platforms and usually allow one screen or one window
to be shared at a time. Wingrid allows multiple live windows to be composed into
one curated layout before projection or sharing.


Question:
How does Wingrid achieve high projection performance without high CPU usage?

Answer:
Wingrid utilizes a GPU-accelerated video pipeline. Instead of constantly capturing and
transferring base64 images over IPC, the renderer requests native MediaStreams via
`navigator.mediaDevices.getUserMedia` using window source IDs provided by `desktopCapturer`.
The GPU handles hardware-accelerated video decoding and canvas composition at 30-60 FPS.


Question:
How does multi-display routing work technically?

Answer:
Electron's `screen.getAllDisplays()` queries native Windows display metrics. The main
process calculates target monitor coordinates `(x, y)` and creates a frameless,
fullscreen `BrowserWindow` on that monitor, passing a layout identifier (`?layoutId=...`).
IPC events continuously broadcast layout state updates from the operator dashboard to
the published window instance.


Question:
Why were speech-to-text live captions included and how do they work?

Answer:
Live captions improve accessibility in classrooms and church environments.
Microphone audio is captured and streamed via WebSocket to AssemblyAI in the main
Electron process (protecting API keys and bypassing CORS), with fallbacks for local
Whisper transcription and Web Speech API. Transcribed text is broadcast via IPC to render
as live caption tiles or floating overlays.


Question:
Why was remote viewing added?

Answer:
Remote viewing was added to extend Wingrid into a network-aware environment.
It allows Wingrid machines on the same local network to discover each other and
request permission-based screen viewing. This is useful in environments where
content exists on a presenter's laptop but needs to be coordinated by an operator machine.


Question:
Why use WebRTC for remote screen sharing?

Answer:
WebRTC is designed for real-time peer-to-peer media streaming. After WebSocket
signaling completes SDP exchange, video streams flow directly between the two machines over LAN.
This minimizes latency and avoids routing high-bandwidth video through a central cloud server.
